1構想の現在地（1段落サマリ）

Claude Code / Codex などのAIエージェントで開発・資料作成・業務自動化を行う際、「設計意図・現状のコード構成・動作・テスト・エージェントの記憶層(ルール)」が単一のライブな真実として1画面で可視化されないことが痛み。これを、フォルダ＋ファイルで構成された移植可能な基幹（＝単一ソース）の上に、タスク⇄キュー⇄変数のデータフローを主画面としたコックピットUIを被せて解く。AIと人間が同じ盤面を見て、自然言語指示から仕様書・設計書を自動生成し、実装・動作・テスト結果まで同一画面で追える。組込み(STM32/FreeRTOS)を最初のドメインモジュールとしつつ、殻は他ドメインへ差替可能にする。

2背景と目的（最新・拡張ビジョン）

直近セッションで示された、当初レポートより広いビジョン。§3〜§7の「組込み特化」結論とは緊張関係にある（→ §8で要再検討）。

背景

① 全タスクを一つのUIで

Claude Code / Codex によるアプリ開発・資料づくり・ビジネス導線の自動化など、あらゆるタスクを、ひとつのアプリ（またはHTMLのような単一UI画面）上で完結させたい。ツール/コンソール/ファイルを行き来する認知負荷をなくす。

② 基幹はフォルダ＋ファイルで移植可能に

OSや、将来類似アプリが出た際にも移植できるよう、基幹システムはフォルダとファイルで構成する。基幹をアプリに閉じ込めて移植不能にしない（UIは基幹の上に乗る"表示層"に留める）。＝ ベンダーロックイン回避・長寿命化の設計思想。

目的

目的意味 / 補足
単一ソースで現状のコード構成・動作・テストを可視化散在ファイル/コンソールでなく、1つの真実から構造・動作・テストを常時描画。状況把握レポートの乱造を撲滅。
自然言語指示＋現状コードから仕様書・設計書を自動生成AIへの指示内容と実コードを突き合わせ、仕様書/設計書を自動生成・追従更新。ドキュメントを"別作業"にしない。

3これまでの結論（競合・市場）

  1. 「統合体は存在しない」は不正確。 マスター図→実装→テスト→検証→セキュリティの統合は、組込みでは MBD/MBSE（Simulink/Stateflow＋Embedded Coder＋Polyspace＋Test）として20年来成熟。概念の市場性は実証済み。
  2. 本当の空白＝4条件の同時成立。 (a) 汎用LLMエージェントが任意コードを書くAIネイティブ、(b) 制御則でなく通信/プロトコル/アプリも含む汎用、(c) 個人/中小が買える安価軽量、(d) 検証/テスト/セキュリティを1モデルに統合。各社は一部しか満たさない。
  3. 競合は6カテゴリに跨る：①汎用ビジュアルPL(歴史的に失敗多)②コード可視化(収益化難)③仕様駆動開発SDD(超激戦/Web中心)④ビジュアル⇔コード双方向(新興・先行者あり)⑥MBD/MBSE(既存王者)。SMB組込み目線では PlatformIO が実質インカンベント（競合でなく統合先候補）。
  4. タイミング： MathWorksが2026-04にMBSE×エージェントAIへ着手＝王者参入前に楔を打つ必要。

4差別化の定義（2軸の掛け算）とSimulink論点

差別化テーゼ（確定版）： AIと人間が「単一のライブな真実」を共有し内部構造を正確に指定 → 実装・動作・テストが常に1枚の階層ダッシュボードに正しく可視化。＝レポートを別途作らせない／記憶層(ルール)も見えて編集できる／動作・テストも同ソースから出る。

差別化は2軸の掛け算（混ぜると弱くなる）

軸中身役割
能力軸単一ライブソース型コックピット（§5の4原則）。本当の発明。LLM普及で初めて生まれた痛み（ドリフト/レポート乱造/記憶層の腐敗）を解く。なぜ選ばれるか。ただし横断的痛み＝水平勢と同じ海。
堀軸特定ドメインの内部構造を"正確に指定"できる縦深＋創業者の専門資産（組込み: STM32/FreeRTOS/LwIP/Modbus）。なぜ大手に潰されないか。Webは構造が緩く価値が薄い＝組込みで跳ねる。

Simulink論点の正確化（専門家に崩されない言い方）

「Simulinkのコード生成は黒箱だから差別化」は誤り（model→Cはブロック単位でトレース可・sim一致が売り）。正しくは下表。

レイヤSimulink本構想
論理 model→C透明・トレース可（強み）同等は狙わない（敬意）
物理 C→バイナリの実現構造モデルに映らない（不可視）実現された内部構造をライブに映す
モデル外(手書き/糊/統合後)単一画面に載らない手書き＋AI生成を含む全体を1ソースに
AIエージェント不在（決定論生成）LLM前提。ドリフト/レポート/記憶層まで対応

5プロダクト設計思想（4原則）とアーキテクチャ原則

① モジュール式・成果物に合わせ入替

「殻(shell)＋ドメインモジュール」の二層。v0は組込みモジュール。殻は将来Web/他へ差替可。＝ 能力軸(殻)×堀軸(モジュール)の具現化＋需要が薄ければモジュール差替で延命。

② ルールのカード化・インタラクティブ

記憶層の全ルール/制約をカード化。出典・矛盾・陳腐化を可視化し、有効化/変更/削除を直接操作。＝ 既存ツールが構造的に持たない"記憶層インスペクタ"。

③ 仕様のシングルソース管理UI

仕様=単一の真実。動作状況・テスト結果も同ソースから派生表示。別ファイルに散らさない。＝ 状況把握レポートの乱造撲滅。

④ グリッドUIで整然配置

各ペインをグリッド配置（ドラッグ/リサイズ）。1画面でAIと人間が同じ盤面を操作。

アーキテクチャ原則（拡張ビジョン由来）

  • 基幹＝フォルダ＋ファイル（移植可能）： 単一ソースの実体は spec.yaml / rules/*.md / design/*.md 等のプレーンファイル。UIはその表示・編集層に過ぎない。基幹をアプリバイナリに閉じ込めない＝ロックイン回避・長寿命。
  • UIはレンダラ： 単一UI画面（アプリ or HTML）は基幹ファイルを描画/操作するだけ。別OS・将来の類似アプリでも同じ基幹を読めば移植成立。
  • modular-ready, not modular-now： モジュールAPIだけ設計し、v0で作るのは1モジュールのみ（一人開発の完成性を守る）。

主要インタラクション（導線）

  • 機能フロー選択（左）→ 該当サブフローを強調（他は減光）＋説明＋テスト結果を表示。＝「全体像を見ながら機能単位で確認・指示」。

7事業性（需要・競合・収益）

狙う顧客：大手が来ない"小さく強い"ゾーン

giantが構造的に来ない交点＝安価 × 非MATLAB × 縦深(組込み) × AIエージェント補完。買い手は個人でも大企業でもなく小さな商用ショップ（小規模ファーム/IoT受託、独立コンサル、ハード系スタートアップ）。ビジネスゆえ払い、小さいゆえセルフサーブで完結し、大手の射程外。

8★未解決の論点（再検討してほしいこと）

本資料の中核。順位は「事業を殺す可能性の高い順」。再検討者は各項を「結論が誤っている前提」で叩いてほしい。

1特化(組込み) と 全タスク統一UI の戦略的緊張【最重要】
§3〜§7は「一人開発・低サポート・年1000万で成立させるには絞れ」と結論。しかし§2の拡張ビジョンは「全タスクを一つのUIで」と広げる。これは制約矛盾の再燃。問い： 殻(汎用)＋モジュール(特化)で両立するのか、それとも拡張ビジョンは一人開発を破綻させる罠か。どちらかに倒すべきか。
2需要の実在（組込み×AIエージェント採用層の薄さ）
楔は「Simulinkの死角(汎用ファーム/プロトコル)×AIエージェント」。だが組込み層はAIコーディング最遅採用層の可能性。TAM＝「AIエージェントを日常使い×ドリフトに痛み×払う」組込み者は薄いかも。＝ 最初に潰すべき仮説。
3「自動で最適構成」の実現可能性が曖昧
§2目的の一つだが定義が未確定。何を"最適"とし、何を入力に、どう検証するのか。誇大機能になりやすい。スコープから外すか、具体的な小問題に落とすべき。
4双方向同期（コード⇔図/仕様）の技術的難所
図→コードは容易だが、人が書いたコードを図/仕様へ正確に戻す逆方向はAST/意味解析が必要で破綻しやすい。v0は「設計した部分だけ片方向＋drift検出」に割り切る案だが、"現状コードの可視化"(§2)と両立するか要検証。
5v0の主役ペイン未確定
候補：①構造/データフロー可視化（デモ一目瞭然・慣性に勝ちやすい）②記憶層ルールカード（新規性最高だが教育コスト）。1つに絞ればv0スコープが締まる。未決。
6スペック形式（単一ソースのスキーマ）未定
基幹＝ファイルなら、そのspec.yamlのスキーマが全ペインの土台。構造/動作/テスト/ルールをどう1形式で表すか。ここを決めないと全機能が浮く。
7収益モデル：法人少数(高単価) vs 小ショップ(セルフサーブ)
低サポート制約とは小ショップ・セルフサーブが整合的だが、"開発者は払わない"逆風と低ACVの解約面リスク。ブレンドが妥当か、Shop単価$159が現実的か要検証。
8移植可能な基幹 と リッチUIの両立コスト
「基幹はプレーンなファイル、UIは表示層」は美しいが、リッチな操作・ライブ描画を薄い表示層で実現するのは実装負荷大。一人開発で成立する境界線はどこか。

今週できる最小検証（コストほぼゼロ・再掲）

  1. 自分のEnergyBox開発で、状態機械＋Modbusマップを1枚の図で定義→YAML化→Claude Codeに渡す、を手作業で1回（人力プロトタイプ）。効果を体感・計測。
  2. Simulink/Embedded Coderを実評価し「Simulinkでは作れない/割に合わない部分」を箇条書き（＝差別化仕様の核）。Atlarix/Kiro/Eraserも触る。
  3. r/embedded等で「複数案件を掛け持ちして、AIに毎回ハード文脈を説明し直すのが地獄な受託/コンサルの人いる?」(§7課題④直撃)。LP＋事前登録20件を需要閾値に。
